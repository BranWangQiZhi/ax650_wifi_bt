## 关键突破：DTB 缺少 SDIO 支持，用「等长改名」绕过签名校验

**根因**：板上 DTB（mmcblk0p6）的 `sdhc@30E00000` 仍带 `no-sdio`，内核不会做 SDIO 枚举。
内核 config 已开 BT/cfg80211，缺的只有 DTS 补丁。

**签名机制**（逆向结论）：
- p6 分区 = 1024 字节 AXERA 头 + 原始 DTB；头部 0x10=payload 大小、0x14=SHA-256(payload)、
  0x1B8-0x2C4 = 每镜像 RSA/ECC 签名（不可伪造，改头必失败）。
- U-Boot `verify dtb image_header` **只验签名，不重算 payload 哈希** → payload 可原地改，
  只要**文件大小和头部字节完全不变**即可通过校验。

**做法（v4，已验证通过）**：
- 字符串表"等长改名"：`cap-sd-highspeed\0`(16B) → `cap-sdio-irq\0`+填充（该串仅 mmc1 使用）
- mmc1 的 `no-sdio` 属性：只改 FDT struct 里的 nameoff(4 字节) 指向已有 `no-sd` 串，
  **不动 `no-sdio` 字符串本身**（eMMC 节点 sdhc@28000000 也用它，共用字符串！）
- 教训：v3 曾直接改 `no-sdio` 字符串 → eMMC 也丢 no-sdio → 内核对 eMMC 发 CMD5
  （SLEEP_AWAKE）导致 rootfs 读取 EIO、boot 失败。v4 修正后 rootfs 正常挂载。

**工具链（都在 .workbuddy/）**：
- `ssh_run.py` SSH 执行；`uboot_serial.py` U-Boot 串口交互（COM3，提示符同步、
  注意：U-Boot 数字参数按十六进制解析、不支持 &&、';' 可用、会 WDT 复位清环境变量）
- `tftp_server.py` 最小 TFTP（U-Boot tftpboot 用，PC 侧 192.168.137.1，加载到 0x150000000
  再 mmc write，因为 0x110000000 是保留内存）；`ymodem.py` ymodem 发送（128B 块才稳）
- 写 p6：`mmc write 0x150000000 0xF000 0x182`（386 块 = 197632 字节）
- 烧写后必须冷启动（拔电），热复位会导致 eMMC HS400 初始化失败

**当前状态**：DTB 校验通过、内核正常启动、rootfs 挂载成功、mmc1 已在发 SDIO CMD5，
但 C5 仍无应答（用户反馈 WiFi 模块之前没上电，需确认供电/硬复位）。

## 第二大突破：SDIO 引脚被 IMU 的 SPI 占用（已修复）

排查发现真正的第二层根因：
- `/sys/kernel/debug/pinctrl/4250200.pinctrl/pinmux-pins` 显示 pin 145-150
  （SDIO_DAT0-3/CMD/CLK）被 **`113000.spi`** 占用，功能是 `SPI_M0_MOSI/MISO/CLK`、
  `GPIO3_A11/A12`；而 `sdhc@30E00000` 节点**根本没有 pinctrl-0**。
- `spi@0x113000` 上挂的是 **ICM45686 六轴 IMU**（`icm45686@0` 子节点 + `ax_icm45686` 模块），
  不是 SPI NOR（`/proc/mtd` 为空）。SDIO 槽位与 IMU 共用同一组 pads。
- SoC 上三组独立引脚：`EMMC_*`→sdhc@28000000（eMMC）、`SD_*`→sdhc@28001000（disabled）、
  `SDIO_*`→sdhc@30E00000（本槽位，已确认对应 C5）。
- AXERA pinctrl 驱动**没有实现 set_mux**，debugfs `pinmux-select` 一律 EINVAL → 只能改 DTB。

**v5+ 做法（工具 `.workbuddy/dtb_patch_v5.py`，可完整重排 FDT struct，用 FDT_NOP 补齐等长）**：
- `spi@0x113000` → `status="disabled"`，删 `pinctrl-0/pinctrl-names/cs-gpios/num-cs`
  及 `icm45686@0` 子节点（IMU 不再探测）
- `sdhc@30E00000`：删 `no-sdio`、加 `no-sd`、`cap-sdio-irq`，
  加 `pinctrl-names="default"` + `pinctrl-0=<&sdio_dat0..3 &sdio_cmd &sdio_clk>`（phandle 0x8f-0x94 新分配）
- 为腾 struct 空间删掉纯 SD 卡专用标志 `sd-uhs-sdr12/25/50/104/ddr50`、`cap-sd-highspeed`、`disable-wp`
- 验证：`pinmux-pins` 6 根引脚全部 `device 30e00000.sdhc function sdio_dat0..clk` ✓
- 烧写方式比 U-Boot 简单得多：直接 `dd if=/tmp/img of=/dev/mmcblk0p6 bs=1M conv=fsync`
  （p6 = dtb 分区，1MB 整分区覆盖，与 U-Boot mmc write 等价），回读 md5 校验

## 第三层根因（未解决）：SDIO 控制器 cardclk 只有 200 kHz

- 症状：`dmesg | grep 'clock div'` → 4 条 `30e00000.sdhc not find suitable clock div`（eMMC 从不报）；
  `Clock: 0x00000000`（SD 时钟根本没开）；`Timeout waiting for hardware cmd interrupt` +
  `Controller never released inhibit bit(s)` 死循环；`/sys/kernel/debug/mmc1/ios` clock=0。
- 时钟链：`cclk_tx_pp_sdio`(gate, 200000Hz) ← `..._divn`(200000) ← `..._sel`(12000000)。
  即 12MHz / 60 = 200kHz。eMMC 对照：`cclk_tx_emmc` = 200MHz（sel 200MHz、div=1），正常。
- 推断：sdhci-axera 用 `clk_get_rate(cardclk)` 当 base clock → 200kHz，算 400kHz 的分频得 0 → 报错放弃。
- 试过无效：
  - `max-frequency` 改 12MHz / 6MHz → 报错不变（说明该值不参与分频计算）
  - DTB 加 `assigned-clocks=<0x19 0x23>` + `assigned-clock-rates=<12MHz/6MHz>` →
    cardclk 纹丝不动（`of_clk_set_defaults` 似乎未生效，或无 warning）
  - debugfs `clk_rate` 是 0444 只读
- 字符串块**没有** `assigned-clocks`/`assigned-clock-rates` 名字，需回收空间：
  `rx-sample-delay-ns\0num-cs\0spi-max-frequency\0` 在 0x728 处连续 44 字节（全部属 SPI 节点，
  可安全回收）→ 正好放下这两个名字（21+16=37B）
- 重要旁证：`kernel-patch/ax650/0002-dts-enable-sdio.patch` 注释写明
  「This slot is shared between SD cards and an SDIO module (**an ESP32-C5 on an SDIO-to-SD adapter**)」
  → C5 是插在 **SD 卡槽**上的，节点选择（30E00000）正确；且该补丁**没有 pinctrl 改动**，
  说明作者那套 DTS 里 pads 默认就是 SD/SDIO 模式、也没有 IMU 抢引脚，且 clock 正常
  → 板上这份 DTB 与项目补丁对应的 `AX650_emmc.dts` 源码版本**不一致**，很可能缺时钟相关配置。

## 21:30 拿到阿里云 SDK（121.40.107.62:/root/sdk -> /data/sdk/AX650_SDK_V3.16.0_...）后的定论

### 一、推翻了此前两个误判

**误判 1：以为「时钟只有 200kHz 导致失败」——错。**
读 SDK `drivers/mmc/host/sdhci-ax650.c` 的 `sdhci_axera_set_clock()`：
```c
unsigned long clk_src[4] = {12000000, 125000000, 200000000};
#define SDHCI_AXERA_MAX_DIV 60
```
时钟源是**硬编码**的，分频计算完全不依赖 `clk_get_rate(cardclk)`。只有 `clock < 200kHz`
（即 12M/60）时才会报 `not find suitable clock div`。mmc core 的 rescan 会按
400k→300k→200k→100k 逐级重试，**最后那次 100kHz 才报错**——报错是「前面都失败」的结果，
不是原因。debugfs 里 `cardclk=200kHz` 也只是 `clk_set_rate(cardclk, 0)`（disable_clk）后的残留值。

**误判 2：以为要给 30E00000 配 `SDIO_*` 引脚组——错，方向反了。**
U-Boot 板级 pinmux 表（`boot/uboot/u-boot-2020.04/board/axera/ax650_emmc/ax650A_evb_pinmux.h`）是铁证：
```
SD_PWR_EN  -> SD_PWR_EN       SD_CLK/CMD/DAT0-3 -> SD_CLK/CMD/DAT0-3
SDIO_DAT0..3/CMD/CLK -> SPI_M0_MOSI/CS2/CS1/CS0/MISO/CLK   ← 给 ICM45686 IMU 用的
```
即：**SD_ 焊盘（pin 139-144）才是 SD 卡槽 = C5 转接卡；SDIO_ 焊盘（pin 145-150）是 IMU 的 SPI。**
之前关掉 IMU、把 SDIO_ 切 sdio_* 全是无用功（v5~v9 都卡在这）。

### 二、v10 / v11 修正

- **v10**：`PINS=sd` —— 30E00000 的 `pinctrl-0` 指向 `sd_dat0..3/sd_cmd/sd_clk`。实测 pinmux 全部归位。
- **v11**：`PINS=sd PWREN=1` —— 再加 `sd_pwr_en` 组（pin 90）。因为 U-Boot 把 pin 90 配成
  `SD_PWR_EN` 功能，而内核没有 pinctrl 引用时 pinctrl 默认把它重置成 GPIO（实测读电平 = 0）。
  同时把 SPI 改为「只摘 icm45686 子节点、保留 SPI 控制器与 pinctrl」（SPI_M0 占 SDIO_ 焊盘，
  与 SD_ 焊盘不冲突），腾出 116 字节，struct 余量 16 字节。
- 脚本 `dtb_patch_v5.py` 现在支持环境变量：`PINS=sd|sdio`、`PWREN=0|1`、`SPI_OFF=0|1|2`、
  `MAXF=`、`CARDCLK=`。

## 15:00 定位到根因：C5 固件未烧录 / 未运行

### 决定性推理

ESP32-C5 的 **SDIO Slave 是纯软件初始化的外设**：上电后硬件不对任何 SDIO 命令应答，
必须由 `firmware/app.bin`（esp-hosted CP 固件，README §2.2 的 BT 版）启动后配置
SDIO 数据通路（日志特征 `SDIO_SLAVE: SDIO datapath mode: SW_AGGR`），卡才会应答 CMD5。

固件没烧 / 没跑起来的现象与我们的观测完全一致：
- 总线 6 根线空闲高电平（引脚为高阻输入）
- CMD5 / CMD8 / CMD52 全部 Resp=0
- `Got command interrupt 0x1` 空槽特征（项目补丁注释里作者实测过同样现象）
- 整板断电 147s 冷启动无效（冷启动救不了"没固件"）

顺带解码了 SDHCI dump：`Cmd: 0x0000341a` → 低字节 0x1a = resp R5 + CRC + index check，
高字节 0x34 = **CMD52**（不是 CMD5）。说明协议栈曾误判"卡存在"、继续读 CCCR，
仍然零应答。

### 补充证据

- 板上 DTB 的 `sdhc@30E00000` 与 SDK 官方 `&sd` **逐项一致**（12 项 `axera,phy-*`
  调参全在、数值相同），唯一差异是 `no-sdio` → `cap-sdio-irq`。软件侧已无剩余可调项。
- U-Boot（原厂板级 pinmux，不经我的 DTB）`mmc dev 1` → `Card did not respond to
  voltage select!` / `mmc_init: -95`（=EOPNOTSUPP，SD 与 MMC 两条路都超时）。
  这不是"没有卡"（没打印 `MMC: no card present`），而是"卡在但不说话"。
- AX650 板上只有 `uart@2016000`(console) 启用，其余 10 个 UART 全 disabled，
  **C5 的 UART 没有接到主控**，只能走外部串口线（README: COM97 / 串口服务器 10.126.41.50:8770）。
- 本机只有 COM3（AX650 console，FTDI 0403:6015），串口服务器 ping 100% 丢包。

## 15:50 问题解决：C5 固件烧录后 WiFi + BT 全部打通

### 烧录过程

- 用户接上 C5 的 USB（VID:PID=303A:1001，乐鑫原生 USB-Serial/JTAG），出现在 **COM4**
- 首次打开报 PermissionError 13（被 MobaXterm 占用），用户关闭后释放
- `python flash_c5.py --port COM4` 四分区全部烧录成功：
  `0x2000 bootloader / 0x8000 partition-table / 0xd000 ota_data_initial / 0x10000 app`
  全部 `Hash of data verified`，末尾 `Hard resetting via RTS pin...`
- 烧完 COM4 报 WinError 31（设备未发挥作用）—— 属复位后 USB 重新枚举的暂态，
  重插 USB 即可（后来用户改接 CP2102N 时该口消失）

### 验证结果（全部通过）

```

/sys/bus/sdio/devices/:  mmc1:0001:1   mmc1:0001:2
[615.476309] esp32_sdio: diagnose_peer_rpc_version: RPC version negotiated: V2
[615.484048] esp32_sdio: process_capabilities: ESP peripheral capabilities: 0xd
            Features: WLAN / BT-BLE / HCI over SDIO / BLE only
[615.718795] esp32_sdio: esp_init_bt: Bluetooth init success
/sys/class/bluetooth/hci0
  BD_ADDR : 10:BD:A3:DF:1E:52   version HCI 14 / mfr 0x02E5   settings 0x0001FE1B (powered=1)
```

WiFi AP：
```
wifi-ap: mode=ap SSID=AX650-SDIO-AP channel=36 if=ethap0
I (404) wifi apsta: ap up. AP SSID:AX650-SDIO-AP ch:36
ethap0: 192.168.4.1/24  MAC 10:bd:a3:df:1e:51
DHCP pool 192.168.4.10-192.168.4.200
```
起 AP 时须 `UPLINK_ENABLE=0`（wifi.conf 默认 uplink SSID=chl 不存在，会反复扫描抢 AP）。

BLE 广播：
```

LE_Set_Extended_Advertising_Data("AX650-C5-TEST"): status=0x00
使能广播 / 关闭广播: status=0x00
```

### 关键结论（写给后来人）

1. **C5 出厂没有烧 esp-hosted CP 固件**，所以 SDIO slave 完全不应答（CMD5/CMD52 Resp 全 0、
   总线空闲高电平、"Got command interrupt 0x1" 空槽特征）。这与 DTB/引脚/时钟无关。
2. 主机侧 DTB 修复（v11：`sd_*` 引脚组 + `sd_pwr_en` + `no-sdio`→`cap-sdio-irq`）是**必要前提**，
   但只有配上固件才会生效。
3. 枚举成功的判据：`/sys/bus/sdio/devices/` 出现 `mmc1:0001:1` 和 `mmc1:0001:2`；
   `capabilities: 0xd` 表示 Wi-Fi + BT + HCI over SDIO。
4. `Controller never released inhibit bit(s)` 出现一次后成功属正常（第一次 CMD 超时后重试）。

### 遗留

- 用户后来接的 **CP2102N**（VID_10C4:PID_EA60）缺驱动，设备管理器 Code 28。
  官方驱动站点本机下载超时/403；`pnputil` 需管理员。需要用管理员执行
  `pnputil /add-driver <CP210x>.inf /install`，或直接用 C5 原生 USB（303A:1001）当串口。
- 待办：把 v11 DTB 方案与"必须烧固件"的结论回写 `kernel-patch/` 与 README。

```

```

SSID=AX650-SDIO-AP  ch=36  password=ax650sdio
hci0    BD_ADDR 10:BD:A3:DD:A5:9E  HCI 14 / mfr 0x02E5

第二颗 C5：USB 序列号 `10:BD:A3:DD:A5:9C`，WiFi MAC `...:9D`，BT BD_ADDR `...:9E`

### 新增：开机自动加载（已部署并验证）

## 18:15 用户问「走 BT PAN 让板子↔PC 传数据，难度大吗」→ 结论：PAN 不可行

### 判定（SSH 实测证据，非推测）
- 控制器 BLE-only：`capabilities 0xd` / `BLE only`；`supported_settings=0x0001FE1B`
  无 BREDR 位(bit7=0x80)，`current=0x201`(powered+LE)
- 内核 `/proc/config.gz`：`CONFIG_BT_BNEP / RFCOMM / HIDP is not set`，全盘无 bnep.ko
- rootfs 无 bluetoothd/pand/hciconfig/bluetoothctl（无 BlueZ）
→ PAN 要 BR/EDR + BNEP + BlueZ 三层，本板全缺。截图那种「一套 AF_INET 代码靠配置切
  WiFi/BT」只对 WiFi 成立；PC 侧虽有 Intel BR/EDR+BLE 和 PAN 适配器(169.254.x.x)也没用。
  真做 PAN 需换经典蓝牙控制器 + 重编内核 + 移植 BlueZ，属改系统。

### 关键 bug：BLE 广播名解析为空

**正式发布仍应重新交叉编译修复后的源码**，补丁只是无工具链时的应急手段。
